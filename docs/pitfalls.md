# 7. 踩坑与验证清单

每条都是**真实故障 → 根因 → 修法 → 怎么验证修好了**。

---

## 1. `503 no_healthy_account`：整个工作流突然全挂

**现象**：请求报 `503 {"code":"no_healthy_account"}`，但 `/healthz` 显示账号「健康」。

**根因**：上游 429 是**账号 × 模型**独立的。四个账号先后在**同一个模型**上被打到限流，
网关把这个组合逐个冷却 → 该模型「无可用账号」→ 503。
`/status` 的 `healthy` 只反映账号级健康，**不反映「模型级可用性」**。

**修法**（三条一起上）：

1. `cooldown.soft_rate_max` 调小（2h → **30m**），恢复更快；
2. 加**模型降级链**（自动切档 + 自动切回，见 [pool-and-fallback.md](pool-and-fallback.md)）；
3. 加号（把「同模型可服务账号数」做大）。

**验证**：`/status` 里该模型的 `rate_limited_models` 是否清空 + 日志出现该模型的 **200**。

## 2. 看板面板「主区域全空」

**现象**：侧边栏能点、能选中，主区域什么都没有；宿主日志干净。

**根因**：React 错误 **#62** —— `style` 传了**字符串**而不是对象。
一个表格单元格写错，**整棵主树被卸载**。

```js
h('span', { style: dimmer }, '—')            // ❌ dimmer 是颜色字符串
h('span', { style: { color: dimmer } }, '—') // ✅
```

**修法**：改对 + 加自检 + 让 client 把渲染异常上报给宿主诊断路由。

**验证**：浏览器里真的看到面板（截图），且 `GET /<ROUTE>/diag` 无异常记录。

> 教训：**宿主侧「没报错」不代表前端没事**。一定要有 client → host 的上报通道。

---

## 3. 热重载后「路由只剩一个」

**现象**：第一次装好可用，热重载后部分接口 404。

**根因**：热重载重新注册同一路径 → `duplicate exact route` 抛错 →
如果这个抛错发生在 `apply` 中间，**后面的路由/工具全都不会注册**。

**修法**：注册前清掉本插件前缀的残留路由 + 每一步独立 try/catch（见 [panel-plugin.md](panel-plugin.md) 坑 2）。

**验证**：连续热重载 3 次，每个路由都 200。

---

## 4. 「服务明明存在，插件却说不可用」

**根因**：访问**未声明**的服务会**抛错**（不是返回 undefined）。
把多个候选路径写在**一个表达式**里时，第一个抛错就把整条吞掉了。

**修法**：每条路径各自 try；并加一个诊断路由把候选路径逐个报告（`has / own / proto / hasList`）。

**验证**：诊断输出里目标路径 `hasList=true`。

---

## 5. 网关被「连带杀死」，且自己不会回来

**现象**：手动重启网关后，过一会儿发现端口没人监听。

**根因**：启动方式让网关成了调用者进程树的子进程；外层被 **job 对象回收**时，
整个树被一起杀掉（脚本注释里写着「脱离 shell」，但在这类环境下不一定成立）。

**修法**：① 用 `cmd /c start /b` 之类真正脱离进程树；② **加看门狗**（30 秒自检 + 幂等启动脚本）。

**验证**：手动 `kill` 网关进程，等 30~40 秒，`watchdog.log` 出现
`gateway NOT healthy (probe #1) -> running start` 且 `/healthz` 恢复。

## 6. 成本账归因陷阱（最容易得出相反结论）

**现象**：网关 `/panel/api/balance_all` 的 `model_costs` 显示
「标称免费的模型 = 0.13 分/千token」，而主力模型只有 0.002 —— 完全反直觉。

**根因**：它的算法是「把两次余额刷新之间的消耗记到**最后使用的模型**上」：

- 并发流量被算到错误的模型头上；
- 每日领奖的**加分**也被反向记进去；
- 样本少时抖动极大。

**修法 / 正确测量协议**：

1. **等一个余额刷新周期**（`balance_refresh_minutes`，默认 5 分钟）再取基线；
2. **单模型窗口**：这一段时间只打一个模型；
3. 从**请求日志**核对窗口内该账号有没有别的流量（有就说明测量被污染）；
4. 再等一个刷新周期读余额差；
5. 拿**两次不同模型的对照**做相对判断（比绝对值可靠）。

实测结论（用上述协议）：标称免费的那个模型**阶段余额 0 变化**（确实免费），
而主力模型有正常消耗 —— 与网关那张表给出的结论**相反**。

**验证**：面板上把这张表标注为「归因不可靠，仅供参考」，并写上正确协议。

## 7. 「已完成，但什么都没有」：思考吃满输出预算

**现象**：客户端显示「已完成，用时 X」，但**没有任何回复内容**。长耗时（分钟级）。

**根因（两个叠加）**：

1. `only_reasoning`（不能关思考）的模型本身很慢：TTFB 15~60 秒、吞吐 1~4 tok/s、单轮可达 5 分钟以上；
2. **思考 token 吃满 `max_tokens` 预算时，`content` 会是空的**：
   实测某模型 `max_tokens=4000` 时 100% 复现 —— `reasoning` 6388 字、`content` **0 字**、`finish_reason=length`。

**修法**：

1. 慢/只推理的模型**不要放在自动链首位**，放到靠后档位或仅手动可选；
2. 给这类模型留**足够大的 `maxTokens`**；
3. 必要时把思考档位映射到更低强度（如 `high: medium`）；
4. **检查默认模型**：把模型插到 provider 模型列表**第一位**会连带改变新建会话的默认模型 ——
   用户会「莫名其妙」全跑在慢模型上。

**验证**：抓流式响应，逐帧统计 `content` 与 `reasoning_content` 的长度：

```python
# 关键指标：content 长度是否为 0；finish_reason 是否为 length
content += delta.get("content") or ""
reasoning += delta.get("reasoning_content") or ""
```

## 8. 「改了配置文件却没生效」

**根因**：插件在**加载时**读一次配置 → 之后改文件当然无效。

**修法**：每一拍（30 秒）重读一次，并在状态里暴露来源标记（如 `cfgSource=file:reloaded`）+ 打一条重载事件。

**验证**：改文件 → 30 秒内 `cfgSource` 变成 `file:reloaded`，事件流出现「配置已重载」。

---

## 9. 「模型已从链里删掉，但几个会话永远留在旧模型上」

**根因**：会话管理逻辑的过滤条件是「模型在当前链内」→ 被删掉的模型上的会话被跳过。

**修法**：额外放行「曾经被我们切过」的会话（有切换记录）→ 让它们迁到新目标。

**验证**：删一个模型后，原来挂在它上面的会话在 1~2 拍内迁走。

## 通用验证清单（每步都别只看「进程在」）

```bash
# ① 存活
curl -s http://127.0.0.1:<PORT>/healthz
# ② 池子健康 + 模型级可用性（后者才是关键）
curl -s -H "authorization: Bearer $API_KEY" http://127.0.0.1:<PORT>/status
# ③ 真打一发（永远别用 /healthz 代替）
curl -s -H "authorization: Bearer $API_KEY" -H 'content-type: application/json' \
  -d '{"model":"<MODEL>","messages":[{"role":"user","content":"hi"}],"max_tokens":8}' \
  http://127.0.0.1:<PORT>/v1/chat/completions
# ④ 日志在写、且没有新的错误
tail -n 5 <GATEWAY_DIR>/logs/out.log; tail -n 5 <GATEWAY_DIR>/logs/err.log
# ⑤ 看门狗在跑（杀掉网关等 40 秒）
# ⑥ 插件路由 + 诊断
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:<HOST_PORT>/<ROUTE>/data
curl -s http://127.0.0.1:<HOST_PORT>/<ROUTE>/diag
# ⑦ 降级链状态 + 配置来源
curl -s http://127.0.0.1:<HOST_PORT>/<ROUTE>/fallback
# ⑧ 今日领取记录
grep -E 'checkin|panel: 队列 growth' <GATEWAY_DIR>/logs/err.log | tail -n 10
```

## 一条经验

**每个「成功」都要有一个可复现的观测点**（一条命令、一个字段、一行日志）。
这次遇到的 9 个故障里，有 4 个的共同特征是：**「进程活着、接口 200、但实际不可用」**。
所以：**能用真实请求验证的，绝不看健康检查。**
